AI/ML-Based Intelligent Anomaly Detection for Automatic Weather Stations (AWS)

Title

SkyGuard AI: Intelligent Real-Time Anomaly Detection System for Temperature, Pressure, and Humidity Sensors in Automatic Weather Stations

Background

Automatic Weather Stations (AWS) are critical components of modern meteorological observation networks. These stations continuously monitor atmospheric parameters and provide real-time data for weather forecasting, climate monitoring, disaster management, aviation, agriculture, and scientific research. However, AWS observations often contain anomalies caused by sensor malfunction, communication failures, calibration drift, power fluctuations, harsh environmental conditions, and data corruption. Erroneous observations can significantly impact weather forecasting accuracy and decision-making systems. Traditional threshold-based quality control methods are often insufficient for identifying complex or hidden anomalies in meteorological data streams.

Problem Statement

Develop an AI/ML-based intelligent anomaly detection system capable of automatically identifying abnormal, inconsistent, or faulty observations from Automatic Weather Stations in real time using only the following parameters:

  • Temperature (°C)
  • Atmospheric Pressure (hPa)
  • Relative Humidity (%)

The system should distinguish between genuine meteorological events and sensor/data anomalies while minimizing false alarms and enabling scalable deployment across large weather observation networks.

Objectives
  • Detect anomalies in real-time AWS data streams.
  • Identify sensor faults, spikes, frozen values, and communication errors.
  • Learn normal temporal and seasonal patterns of temperature, pressure, and humidity.
  • Perform multivariate consistency analysis among atmospheric parameters.
  • Provide confidence scores and explainable AI-based reasoning for detected anomalies.
  • Predict possible sensor degradation and maintenance requirements.
  • Optionally suggest corrected/imputed values for anomalous observations.

The position, in one line.

Everyone else builds a better buddy check. We measure ours against IMD's own 2015 spatial regression test — then solve the station it structurally cannot reach, using a reference clock the station already carries in its own barometer.
The ML spine.

Everyone puts the ML in the anomaly scorer. We put it in the reference. The model's job is to predict what this station should have read; the anomaly is the subtraction. This is the defensible framing because a better reference improves every fault class at once while a fancier scorer improves none — and it follows from the arithmetic, since drift latency is governed by the noise of the reference, not by the cleverness of the detector.

The AI architecture — a panel that must corroborate

The problem statement asks whether AI can build a “self-aware and self-healing weather observation network”. That phrase has to cash out as an architecture or it is decoration. This is the architecture, and the word agent here means an autonomous specialist checker with its own evidence source — not a language model.

The belief state — what the system actually remembers

A pipeline judges each reading from nothing and forgets it. The architectural change is that every sensor carries a file that persists and updates. Roughly 1,000 stations × 3 sensors is ~3,000 of these, each a few dozen bytes.

The anomaly becomes a by-product of the update, not the goal of the computation. That single inversion is what makes the separate objectives in the statement one mechanism instead of seven features: degradation prediction is reading the drift rate off the file, the confidence score is the state's own uncertainty, and the root cause is whichever part of the file moved.

The nearest operational precedent is variational bias correction, which ECMWF has run since 2006: each instrument's bias coefficients sit inside the analysis control vector and are estimated jointly with the atmospheric state, every cycle, rather than computed offline. The architecture is twenty years proven — what is unclaimed is turning it toward diagnosing the instrument rather than correcting the forecast.

Gandin 1988 is the one that matters. Combining a complex of residuals rather than thresholding one is the founding idea of meteorological QC, and it is nearly forty years old. The rule as first written was not falsifiable. This is the fix.

The original wording — “corroboration must come from agents whose evidence does not overlap” — asserts independence rather than measuring it, and the ensemble literature is emphatic that assumed diversity does not deliver.

  • Kuncheva & Whitaker (2003) tested ten diversity measures and found the relationship between diversity and ensemble accuracy “weak and inconsistent on real problems”. Accuracy does not rise monotonically with diversity under any of them.
  • Knight & Leveson (1986) had 27 programs written independently from one specification and ran a million test cases. Versions failed together far more often than independence predicts, correlated through shared interpretation of an ambiguous spec. The result has survived forty years of attack.
  • Common-cause failure has a floor. In reliability engineering the beta-factor model puts deliberately diverse redundant subsystems at roughly 10−3. Diversity buys about one order of magnitude and cannot be driven to zero.
The rule, restated so it can be checked: corroboration must come from checkers whose measured double-fault rate under the prevailing weather regime is below a stated threshold — not from checkers we believe to be independent.

The deliverable is a 6×6 error-correlation and double-fault matrix computed on labelled data and published, reported separately for calm and for extreme conditions. Independence that holds on average and collapses in the tail is exactly the failure that matters, and a single aggregate number hides it.

Our own concrete common causes, written down rather than discovered later: physics, spatial and temporal checks may all reduce to a departure from the same background field; severe weather breaks the spatial and temporal smoothness assumptions at the same moment; one wrong station elevation poisons the physics, spatial and pressure-tide checks together; and one person writing all six checkers to one internal specification correlates their blind spots by construction.

How it must be evaluated

There is no benchmark discipline for multi-agent systems — current surveys say evaluations are run in narrow bespoke scenarios and are not comparable. So a reviewer cannot ask for a standard MAS benchmark. They can ask why we ignored the three established methodologies that do apply.

An untethered UNKNOWN makes any system look perfect. A panel that abstains on 95 % of readings will show a beautiful selective risk. Coverage travels with every number or the number means nothing — this is the most likely line of attack on the whole design.

And the outcome to be ready for: if the panel does not beat its best single checker on that ablation table, the correct action is to ship the best single checker. The ensemble literature says that is a live possibility, not a remote one.

On combining the verdicts

Dempster–Shafer theory is the obvious formalism, because mass on the whole frame represents ignorance explicitly — which is what UNKNOWN needs. But Dempster's rule breaks precisely on our conflict path. Zadeh's counterexample: two sources that almost entirely reject a hypothesis, disagreeing sharply on everything else, combine to give that rejected hypothesis belief 1.0 — because the normalisation divides out the conflict and amplifies whatever rounding error survived. High conflict is exactly when we want more ignorance, and the rule delivers false certainty instead.

Use Yager's rule, which reassigns conflict mass to ignorance, or reliability-weighted averaging before combination — or keep a transparent signature-matrix rule an operational meteorologist can read, and borrow only the belief/plausibility vocabulary.

So what is actually ours

Stripping out everything that is CQC, blackboard or FDI under another name, what remains is specific and defensible: the semidiurnal pressure tide used as a per-station reference clock, which detects timing faults with no neighbour involved and is measured viable on our data; the Level-0 screen on the station itself, which IMD's own 2015 paper records as not implemented; and the work order with a dated onset rather than a flag. Those are worth more than an architecture claim, and they were being buried under one.

What four rounds of research changed

This blueprint was reviewed against the meteorological QC literature and pressure-tested on method selection, explainability and operator workflow. Three findings changed the design materially, and one of them was a factual error. They are stated here rather than quietly fixed, because the corrections are more instructive than the original plan.

Correction 1 — the dew-point check was a tautology. The earlier draft listed Td ≤ T, RH ≤ 100 % and e ≤ es(T) as three independent physics constraints. When Td is computed from T and RH via Magnus, they are algebraically the same inequality. Substituting RH = 100 into Magnus returns Td = T exactly, at every temperature; RH < 100 gives Td < T; RH > 100 gives Td > T. The check reduces to "is reported RH above 100 %" — a range check.

The old flagship example — "dew point 33.1 °C exceeds air temperature 31.2 °C" — implies a reported RH of 111 %. A domain judge spots that immediately. Real cross-parameter physics is in the next section.
Correction 2 — the two-layer split is not the innovation. Every Layer 1 element is a named, standardised test in operational meteorological QC: gross-error/plausible-value, persistence/flat-line, step/temporal-consistency, internal consistency, and spatial-consistency (buddy) checks. An IMD reviewer recognises the whole suite on sight. It stays — as the credibility floor and the explainability substrate — but leading with it as novelty is the fastest way to lose the 25 %.
Correction 3 — health is a state, not an event. The earlier draft conflated "this reading is bad" with "this sensor is deteriorating". They are different objects with different lifetimes and need separate storage, separate update rules and separate UI.

Everything below is the revised plan. Where the reviews disagreed with each other, both positions are given.

The one problem that actually matters

Everything hard compresses into one line of the statement's own text: distinguish between genuine meteorological events and sensor/data anomalies.

A real weather event looks statistically like an anomaly. A cold front produces a sharp pressure fall, a temperature fall and a humidity rise — three simultaneous multivariate excursions. A naive detector flags it. Flag enough real fronts and IMD stops trusting the system, which is the same as it not existing.

The discriminator is cross-channel coherence, not magnitude

Real phenomena move all three parameters in a physically consistent pattern. A failing sensor moves one. All four reviews converged independently on this being the strongest available signal, and it uses exactly the three parameters the statement allows.

On drift, honestly

Sensor aging drift is of order 0.01–0.05 K/day. Weather variability is two to three orders of magnitude larger. No single-station statistic fixes that — the neighbour-difference series is the only thing that does, and it works because weather is spatially coherent while drift is not.

Detection latency scales as σdaily-difference / slope. Measure your own σ on a clean period and publish the latency-versus-slope curve. If it comes out at weeks rather than days, say so. A team that reports "3–6 weeks at 0.02 K/day, here is the measured curve" is far more credible than one claiming real-time drift detection.

What you cannot do statistically: separate sensor drift from a genuine change in the station's environment — vegetation growth, a new building, a resited screen. They are identical in the data. Route it to a metadata and human-confirmation step, and say so on the slide. Judges will respect it; claiming otherwise is a hole they will find.

The learned layer, revised

Replace 288 cells with harmonic regression

A per-(station, hour, month) baseline is 12 × 24 = 288 cells per station per variable. With a year of hourly data that is about 30 samples per cell — and MAD from 30 samples is very noisy. It also creates discontinuities at hour and month boundaries, and it has no answer for a brand-new station.

Instead: two to three diurnal harmonics plus two annual harmonics, fit robustly (Huber or quantile regression). Roughly ten parameters instead of 288, continuous everywhere, usable with far less history, and it degrades gracefully. Add hierarchical shrinkage — station → region → climate zone — so day one of a new station is answerable.

Widen the vector so it sees dynamics

Mahalanobis on three residuals is a point detector — structurally blind to frozen, dropout, drift and noise burst, which is four of the seven classes. Do not build the architecture around it. Make it earn its place by widening to six dimensions:

z = [ z_Td, z_q, z_P, Δz_Td, Δz_q, Δz_P ]

Now it can distinguish "T dropped 5 K while P and RH did nothing" (fault) from "T dropped 5 K while P jumped and RH jumped" (gust front). That is a real gain, and it is the multivariate consistency objective answered concretely.

For robust covariance, Fast-MCD is fine at d = 6 but must be fit on clean data or masking makes it absorb the anomalies it should catch. OGK or a pairwise comedian estimator is cheaper and often adequate. Covariance is seasonally non-stationary — fit per season, or document the degradation.

Benchmark honestly, and publish the loss. If Isolation Forest does not beat median/MAD on your harness, report that. "We benchmarked the fancy thing, the simple thing won, here is the curve" is a strong look with technical judges, not a weak one.

Explainability, done properly

The framing problem

"We use SHAP to corroborate" reads to a judge as we did not really do it. The organisers named the tool, and Explainability is 10 %. The fix is not to bolt SHAP onto the physics layer — it is to put SHAP where it is genuinely the right instrument: the signature classifier, whose features are already human-meaningful (identical_run_length = 47, spatial_zscore = 0.3, recovered_next_sample = true). A Shapley attribution over those is a real decision audit.

State the policy explicitly: deterministic violations are explained by the law they broke; learned detections by exact Shapley attributions; root cause by TreeSHAP over named diagnostic features. That defends the design instead of apologising for it.

Physics-propagated confidence — the strongest result available

A violation is not automatically probability 1. RH reading 100.4 % with ±2 % instrument uncertainty is not a violation; 111 % is. Propagate the stated probe accuracies through Magnus to get the standard uncertainty on the violation margin, then

confidence = Φ( margin / u_margin )

So the alert reads: "exceeds by 1.9 °C; combined standard uncertainty 0.45 °C; 4.2σ; p(invalid) > 0.999". Calibrated from metrology, needing no training labels at all — and it automatically suppresses the marginal-violation false alarms that would otherwise flood the operator at high humidity.

Magnus coefficients differ over water and over ice. Using the water set below 0 °C manufactures spurious violations at high-altitude and northern stations. Select by temperature and document the switchover.

Exact Shapley, not approximate

At six to eight features, exact Shapley is 2d = 64–256 coalitions — microseconds. KernelSHAP's sampling approximation exists to handle d ≈ 200; using it at d = 6 is strictly worse than exact enumeration. Say that in the writeup; it shows you understand what SHAP is.

For the Mahalanobis score, use the conditional value function, v(S) = z_Sᵀ (Σ_SS)⁻¹ z_S — the inverse of the submatrix, not the submatrix of the inverse. The interventional form evaluates the score at combinations that cannot physically occur. Each attribution then reads as "surprise in this channel not already explained by the others", which is exactly the correlation-aware answer.

Never put a derived quantity in the SHAP feature set alongside its parents. Td is an exact function of T and RH. Include T, RH and Td and Shapley splits credit among perfectly dependent features — every attribution looks small and the output reads "nothing is important". Pick a basis and hold it. Derived quantities belong in the physics screen as constraints, not in the learned feature set.

For the operator view, compute grouped Shapley over three or four groups — temperature channel, pressure channel, humidity channel, cross-channel consistency. Group attributions are stable where individual ones are not, and four groups is sixteen coalitions. Keep per-feature attribution in the analyst drill-down.

On LIME — reject it, but prove it

LIME's local linear surrogate has an arbitrary kernel width, is unstable across reruns at low dimensionality, and its perturbation sampling generates physically impossible points. Rather than dismissing it: implement it behind a flag, run 20 times per instance, and report the Jaccard overlap of top-k features against SHAP. An evidence-backed rejection scores better than a LIME chart nobody trusts, and it is one afternoon.

Degradation and maintenance

Fit the neighbour-difference residual with robust regression — Huber or Theil–Sen, mandatory, because outliers from genuine faults would otherwise dominate the slope — over a trailing 60–90 days. Then:

TTOS = ( spec_limit − |b0_now| ) / |b1| report the interval, always

Present as "≈ 47 days (18–140)", never a bare number. A wide interval is information.

Do not attempt a Weibull / survival RUL model. You have no failure-history dataset. Any hazard curve you fit would be fabricated. Linear extrapolation of measured drift with honest confidence bounds is defensible in front of a domain judge; an unfittable Weibull is not — and saying so out loud reads as maturity.

Also: TTOS predicts specification excursion, not failure. Label it exactly that way in the UI. Most real degradation is abrupt, not linear.

Add a second, non-drift trigger: variance-collapse time. When the noise component falls monotonically for N days it often precedes stiction failures, which pure drift extrapolation misses entirely.

Sort the work queue by a maintenance priority index, not by TTOS alone:

priority = urgency x criticality x (1 / accessibility_cost)

Criticality is a hand-populated config field — aviation, flood-warning basin, model-assimilation station, ordinary. And add a "nearby also due" indicator: a real maintenance engineer's constraint is travel, not sensors, and batching a field trip is the feature that makes their eyes light up.

Honest limits: if a whole region drifts together — a bad firmware version, a supplier batch — your neighbour reference drifts with it and you see nothing. Mitigate by also regressing against long-term climatology and by monitoring the network-wide mean residual as its own signal. Pressure drift is the most detectable; RH is the hardest and degrades non-linearly at the high end. Below ~30 days of history, show "insufficient history" rather than a number.

Data strategy and injection realism

The statement removes the usual blocker: "Participants may use historical AWS datasets, simulated anomalies, or streaming sensor data", evaluated on "anomaly injected data". Synthetic faults are the sanctioned methodology.

Use real station history for realism (public hourly surface observations give genuine diurnal and seasonal structure, real noise, and real events to avoid flagging) and injected faults for evaluation, where you control ground truth.

The self-flattery trap, and how to structurally avoid it

The dominant failure is injecting only large, obvious faults. Counter it by design:

  • Sweep magnitude and report a curve, not a number. Probability of detection versus anomaly amplitude in units of local σ, at a fixed alert budget. Headline the minimum detectable amplitude at 90 % POD. This single change does more for credibility than anything else here.
  • Include sub-threshold magnitudes. Spikes 2–20 σ. Steps down to the noise floor. Drift 0.005–0.1 K/day over 10–180 days. Frozen 30 min to several days. Noise ×2 to ×20.
  • Hard cases deliberately. Freeze at a value plausible for that hour. Pin RH at 99.9 or 100.5, not exactly 100. Inject a step whose sign matches the prevailing trend.
  • Onset shapes: instantaneous, linear ramp, exponential-asymptote (typical of aging), and intermittent/flapping — a sensor failing for 20 minutes every few hours is extremely common in the field and almost always missed by systems tuned on clean single-episode injections.
  • Inject during real weather events, not only quiet periods. A spike on top of a thunderstorm is what separates a good system from a demo.
  • Multi-fault: drift plus occasional spikes — the realistic aging picture.
  • Negative controls: matched clean windows, plus a distractor set of real events with no injection.

Execution reality

The plan above is achievable, but it is a heavy software engineering lift rather than a weekend project. Four things will decide whether it lands.

1  The injector is the largest single line item — and that is correct

Expect the injector and harness to consume something like a third to 40 % of total effort. Do not treat that as overhead. Evaluation happens on anomaly-injected data, so the injector is the instrument that produces every number you will quote. Spending that share on it is correctly weighted.

Two things make it manageable:

  • It parallelises cleanly. One person owns the injector while others build the residual and physics layers, which have zero dependency on it.
  • Build it in tiers. Three fault types at fixed amplitudes gets the MVP moving in days. Amplitude sweeps, onset shapes and intermittent flapping are refinements you add once the harness is already consuming output.

2  Station density is the gate — answer it in week one

The risk that outranks everything else. The entire spatial thesis — the 20× noise reduction, drift detection, the fault-versus-weather discriminator — assumes neighbours close enough to be correlated. If the network you can actually obtain is sparse, or the stations are hundreds of kilometres apart, that channel degrades badly and much of the design falls back to single-station self-consistency.

Answer it before writing the injector. Pull real station data, compute σ of the pairwise difference series against distance, and find your usable correlation radius. If it is good, everything proceeds. If it is poor, you learn it while there is still time to adjust — not in month three.

The headline result

Calibration drift is detected at 0.01 K/day with recall 1.00, at one alert per station per week. The one mechanism nobody has written down

A baseline refitted on data containing a slow degradation absorbs about 93 % of it and goes blind.

This is ours, it is measured, and it is the reason the objectives above are harder than they look. IMD's documented spatial check — the Spatial Regression Test of You, Hubbard & Goddard (2008) — refits its regression on a 25-hour window centred on the datum being tested. A degradation that develops over months is inside that window by construction, so the reference bends to follow it. The check is not badly built; it is built for a different question.

We measured this three ways and were wrong twice before getting it right. It is not robustness — Huber absorbed more of the ramp than ordinary least squares (0.8 % versus 3.5 % surviving). It is not the neighbour difference — that recovered 2.4 %, worse than the raw residual. It is the freezing, and only the freezing: a baseline fitted on a clean reference period and never refitted on scored data leaves the degradation fully visible.

The adaptive anomaly-detection literature is built on the premise that adapting is good. When the thing being detected is degradation of the sensor itself, adaptation is self-masking. That is a rule with an ablation behind it.

And the same structure appears in NCMRWF's background check. Observations are tested against the previous cycle's model forecast — but that forecast assimilated the same station six hours earlier, and the one before that, and so on. The reference is not independent of the station's own history. A degradation of 0.01 K/day moves the observation and the background together, so the departure stays small and the probability of gross error never rises. Their specified SYNOP temperature error is 1.4 K; a drift takes almost five months to reach it, and by then the background has followed. This is not a flaw in their system — a background check exists to catch gross errors in a single cycle, and it does that well, rejecting under 1 % of temperature reports. It is simply the wrong instrument for a fault that develops slower than the assimilation window, and nothing in their documented pipeline is the right one.

What IMD's published system already does

One substantive public description exists: Ranalkar, Anjan, Mishra, Mali & Krishnaiah, MAUSAM 66(1), January 2015, 93–106, by IMD Pune, describing what was operational at the Central Data Receiving Earth Station. Read it before presenting anything. It runs range checks against sensor and monthly climatological limits; step checks at 1 and 3 hours with per-station monthly thresholds; internal consistency including T < Td − γ; and the Spatial Regression Test described above. It defines a flag vocabulary, and it monitors the network for non-functional and intermittently transmitting stations, battery voltage and GPS lock, emailed to the RIMCs.

That paper is from 2015 and we do not know what runs in 2026. No successor description of the core AWS QC algorithm was found. Vision 2047 sets short-term objectives for AWS-level quality intelligence (below), and sister organisations run their own quality control, and it is substantial. Read directly: Desamsetti, Sharma, Rani & Das Gupta, “Monitoring and quality control of surface meteorological observations at NCMRWF”, NMRF/TR/02/2022. Their Observation Processing System applies a Bayesian gross-error framework: an initial probability of gross error is updated by a consistency check (PGE1), a background check against the previous cycle's model forecast (PGE2), and a buddy check against nearby observations of the same type (PGE3), after which anything at PGE3 ≥ 0.5 is not assimilated. For SYNOP the specified errors are 70 Pa, 1.4 m/s, 1.4 K and 7 % RH. Measured rejection over June–July 2021: under 1 % for temperature, wind and pressure in the background check and under 1.5 % in the buddy check, with humidity around 4 %.

Two claims relayed to this project from a secondary summary do not survive contact with the primary documents and have been removed: NCObsProM contains no “dynamic blacklisting” and no Pass/Valid/Conditional/Reject flag scheme — the words “blacklist” and “flag” do not occur in it at all. Its actual rule for Indian surface observations is a volume monitor: “if the total number of Indian surface observations received during each assimilation cycle is less than 20 % of the mean of the previous 45 days count, then action will be taken by informing the concerned agencies”. That counts arrivals; it does not examine values. And every occurrence of “drift” in the surface QC report refers to drifting buoys, not calibration drift.

Mission Mausam is largely orthogonal to this work, and an earlier draft of this page said otherwise. Its published deliverables (MoES, ₹2,000 crore, Phase-I 2024–26) are new instruments and cloud physics — 50 DWRs, 60 RS/RW, 100 disdrometers, wind profilers, radiometers, testbeds, 10 Marine AWS — plus a substantial weather modification programme. There is no AWS network expansion in the deliverables and exactly one quality-control line: “Evaluating the existing observing network and preparing quality-controlled datasets for model verification.” Its AI/ML objectives are about forecasts and earth system models, not observation QC. A secondary research summary attributes a four-stage QC pipeline with ML fault-versus-cloudburst classification to Mission Mausam; that is not in the primary document and should not be repeated.   • Range, gross-error or climatological limit checks
  • Step or rate-of-change checks
  • Internal consistency between temperature and humidity
  • QC flags exposed to users — a vocabulary was defined in 2015
  • Automated network and station health monitoring
  • Interpolation of erroneous values
  • And never that IMD has no quality control

Speak their vocabulary, not ours

Vision 2047 never uses the word “drift” in the sensor sense — not once in 284 pages. Their terms are accuracy of measurements over time, correction factors, self-monitoring and diagnostic capabilities, automated calibration planner. Use those. Elsewhere: Level-0 and Level-1 QC, SRT, ES (Central Data Receiving Earth Station, Pune), RIMC, NDC, SLP for station level pressure and MSLP for the reduced value — IMD derives MSLP at the Earth Station, which answers a question this page previously listed as needing human verification. Their paper also notes that 10 m of elevation error produces about 1 hPa of error in MSLP.

Open questions we have not resolved

  • Does the 2015 system include a persistence / flat-line check? A direct read of the paper found four checks and no persistence test; a secondary research summary states persistence checks were present. The two conflict, and it matters because a flat-line detector is one of the things we would otherwise claim. Resolve from the primary paper before saying anything.
  • Which flag vocabulary is IMD's? A direct read gives 0 QC Not Done · 1 Good · 2 Doubtful · 3 Erroneous · 4 Changed/Interpolated · 5 Missing. A secondary summary gives an incompatible set. Using the wrong one in front of IMD would be a poor way to show we did the reading.
  • Data from the Data Supply Portal is post-processed. Erroneous values appear to be filtered or replaced with missing markers and flag columns stripped from public CSV exports. If so, DSP data cannot be used to demonstrate anomaly detection — the anomalies have already been removed. Verify before paying for a dataset.
  • Inter-station spacing and usable correlation radius for the real network. Still unanswered, still the project's largest risk. The SRT's 2°×2° search box is the only IMD-sourced hint.

Ratio is the diurnal range within a day against the spread of daily means between days. A small ratio means the sun barely moves it, so a fault that does has nowhere to hide.

The synthetic figure overstated the advantage by about 60 % — it claimed working in dew point was 3.7× quieter than relative humidity; on real air it is 2.3×. The direction held, the magnitude did not, and that number would otherwise have gone on a slide.

It also changed the answer: on real observations the most conserved coordinates are specific humidity and equivalent potential temperature, both at 0.45, ahead of dew point. The synthetic run had put dew point first. The coordinate to difference is q, not Td.

Three caveats that travel with all of the above. ARM sites are research-grade and better maintained than a national operational network, so these fault rates are a lower bound on IMD's, not an estimate of them. The stations are North Atlantic, Alaskan and Great Plains — climatically nothing like India, so the conservation ratios will differ there and must be re-measured. And observation-minus-background departures are computed against a model that has already assimilated the station being judged, so they go blinder the slower the fault; our neighbour difference has the opposite bias, which is why the two are complementary rather than competing.

The drift latency is weeks, not real time, and that is the honest answer. The drift section predicted exactly this; it is now confirmed rather than assumed.

Robustness does not protect a baseline from a drift in its own fitting window. Fitted over a window containing a 0.02 K/day drift, the fraction still visible in the residual is 0.035 for OLS, 0.008 for batch Huber, 0.064 for online Huber — the robust estimator is the worst of the three, because a slow drift never looks like an outlier. Only a frozen reference window preserves the signal, which is why the station tier is sent its coefficients and never refits.

Cadence-independence matters for deployment. A 24× change in sampling rate moves σ by 5 %, so the drift result describes a physical timescale and transfers to the 15-minute cadence real AWS report at. But every window in the code is expressed in samples: at 15-minute data the 720-sample scale window is 7.5 days rather than 30, and the 24-sample Hampel window is 6 hours rather than a full diurnal cycle — it would no longer contain the cycle it exists to normalise against. Any redeployment must rescale windows by time.
shield_failure is detected but cannot yet be named, and three fixes were measured and rejected. The fault is switched off by sunset, so the detector fires in short daily bursts and the classifier sees a 4-hour fragment rather than a 400-hour event. Adding a diurnal_gain descriptor changed nothing — an A/B against the pre-change classifier came back identical at 0.595 in both arms, because the template never fired at all. Repairing td_ratio to be measured on diurnal gain rather than the window median moved naming to 0.611 but still never named a shield fault. Widening the run-merge gap to 30 h finally let it fire, and cost more than it gained: naming fell to 0.489 as genuine 1-hour spikes merged into the quiet hours around them and read as weather. One global merge gap cannot serve both a spike and a sun-driven fault; that needs per-hypothesis merging, which is not built. The honest state is: detected, not named.

Caveat on the 15-minute arm: ERA5 has no sub-hourly variability to resample, so that arm is explicitly synthetic. It answers "do the windows scale", not "how good are we on real 15-minute data".
